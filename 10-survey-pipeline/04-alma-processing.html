Step 3 — Processing the ALMA data

Step 3 — Processing the ALMA data

This is the layer the whole thesis stands on: the machinery that turns a downloaded cube into spectra, maps and numbers. It was built and hardened over the whole project (the archived Code pages document its per-galaxy ancestors); today it lives as a reusable Python package, master_thesis/my_code/_step3/.

3a. The data model

A spectral cube is a 3-D array: two sky axes × one frequency axis. Frequencies convert to velocities relative to the target line via the galaxy's redshift (channel_velocities). Three views of each dataset matter:

  • pbcor cube — true fluxes, but noise grows toward the field edge;
  • flat-noise view — pbcor × primary-beam map: wrong absolute fluxes, but uniform noise, so "2σ" means the same everywhere;
  • primary-beam map — also defines where the data ends: pixels with response < 0.2 are discarded (apply_pb_cutoff), because the correction there amplifies noise by ×5 or more.

Two beams must not be confused: the primary beam (the ~30–60″ field-of-view circle, set by the 12-m antenna) and the synthesized beam (the 0.1–8″ resolution element, set by the array configuration). The pipeline reads both from the FITS headers; nothing is hard-coded.

3b. Handling cubes that don't fit in memory

Archival cubes reach 25–60 GB. The package's cube_io.load_cube memory-maps every cube (data stays on disk; only the slices being read enter RAM) — this is what lets a laptop-class machine process the whole sample. Two practical rules learned the hard way:

  • gzip-compressed FITS cannot be memory-mapped — such files are decompressed to disk once (never into RAM) and the scratch copy reused;
  • every per-channel operation streams through the cube channel by channel (moment maps, spectra) rather than loading it whole.

3c. What gets extracted from each cube

  • Moment-0 map (uniform_batch_stage1.py): the tracer cube summed over the line's velocity window, in the flat-noise view, cached as an array for every later stage.
  • Aperture spectra (multi_mask_spectra in uniform_contour_poc.py): given any set of pixel masks, one pass through the cube returns one spectrum per mask — the science aperture, the diagnostic skirt, and up to 16 translated null apertures are all extracted in a single read.
  • Geometry (get_beam_area_pix, beam_fwhm_pix_of): beam areas and widths in pixel units, from the header, used to convert "Jy/beam summed over pixels" into physical Jy.
  • Spectral toolkit (flux.py, known_lines.py): known-line blanking, first-order baseline fit with 3σ clipping, window integration, empirical noise — the actual measurement, described in detail on the next page.

3d. When archive images are not good enough: imaging ourselves

The survey default is to use the observatory's own pipeline-imaged product cubes — uniform provenance, zero per-galaxy choices. But the project also maintains a full re-imaging path from the raw visibilities (used in the detection era, kept operational as the fallback when a product cube is missing or defective):

  1. step1_uvcontsub.py — continuum subtraction in the visibility domain (CASA uvcontsub), fitting line-free channels;
  2. step2_imaging.py — imaging and deconvolution (CASA tclean), producing our own pbcor/pb cubes with controlled channelization.

The archived Code pages contain these scripts with commentary. A validation from the detection era justifies trusting the products: for NGC 3628 the archive product cube and our own re-imaging gave the same flux to within a few percent — so the survey uses products, and the re-imaging path stays in reserve.

3e. Cross-cube operations

  • Mask reprojection (mask.py::reproject_mask): the aperture is defined on the tracer cube's pixel grid and must land exactly on the recombination-line cube's (and later the infrared images') grid — a world-coordinate reprojection, verified on the control galaxies.
  • Beam matching (mask.py::convolve_to_beam): where two cubes' resolutions differ materially, the sharper one is convolved to the coarser beam before comparison (streaming, disk-backed for the large cubes).

3f. Products and bookkeeping

Every stage appends its results to CSV tables under result_v2/_uniform_batch/ as it finishes each galaxy (crash-safe: a re-run resumes where it stopped, skipping completed rows). Figures (per-galaxy diagnostic panels, thumbnails, the gallery) are regenerated alongside. Nothing is edited by hand downstream of the cubes — every number in the thesis can be traced to a script, an input file, and a logged decision.
