Dual-cube analysis pipeline

The analysis pipeline turns an ALMA archival cube (or a pair of cubes) into an integrated HRL flux and an S/N number. It is the same code path for every galaxy in the final sample; per-galaxy parameters (redshift, mask mode, scenario tier) come in through a thin configuration layer.

Stages, in order

Setup

  1. Download — step-1_download.py (emitted by /alma-query) pulls the chosen ALMA product into a per-galaxy scratch directory.
  2. Rename + symlink — step-2_link.py resolves the cryptic archive product paths into stable filenames ({GALAXY}_H30a_pbcor.fits, _nonpbcor.fits, _pb.fits, etc.) inside master_thesis/work_dir/{GALAXY}/.

Analysis

  1. Common-beam convolution — _step3/mask.py:convolve_to_beam uses radio_beam to bring both cubes onto a common synthesised beam (the larger of the two).
  2. Spatial reprojection — _step3/mask.py:reproject_pair puts both cubes on a common pixel grid via reproject.
  3. Mask construction — _step3/mask.py:build_mask thresholds the strong-tracer cube at $3\sigma$, applies a velocity-integration window and a morphological-connectivity filter, then transfers the mask onto the HRL cube.
  4. Baseline subtraction — _step3/baseline.py fits a degree-1 polynomial baseline on line-free channels of the same SPW.
  5. Flux integration — _step3/scan.py integrates the HRL pbcor cube within the mask over the velocity direction.

The pipeline emits a per-galaxy summary.md with the integrated flux, its uncertainty, the S/N number, the mask geometry, and pointers to the diagnostic plots.

Why dual-cube

ALMA SPWs are $\sim 1.875$ GHz wide. Ideally the HRL (e.g. H30α) and the strong-tracer line (e.g. CO(2-1)) fall in the same SPW, so a single cube contains both, and the mask built on the strong tracer can be applied to the weak HRL without further alignment. In archival practice this is the exception, not the rule:

Common configuration Number of cubes Resolution
HRL and tracer in the same SPW 1 trivial
HRL and tracer in different SPWs of the same observation 2 reproject within project
HRL and tracer in different observations (different MOUS-IDs) 2 reproject across projects

The dual-cube workflow handles the latter two by convolving both cubes to a common beam and reprojecting them onto a common pixel grid before mask transfer. NGC 3628 (spw0 = CO(2-1), spw1 = H30α in the same observation) and NGC 5253 X1a (cross-MOUS-ID H30α + CO(2-1) from two separate observations) are both detected through this code path and reproduce published flux measurements to within their stated uncertainty.

When pre-imaged FITS is enough

For all 32 sources in the final sample, the pipeline-imaged *.pbcor.fits product (Scenario B) was used directly. Re-imaging from MS (Scenario A) was investigated for NGC 4418 (an ultra-compact obscured nucleus) and NGC 1097 (a nuclear-bar starburst), but cancelled when other selection criteria gave a low predicted detection probability — the CASA pipeline cost (several hours and $10$–$50$ GB of intermediate disk per source) was not justified.

Custom imaging is the exception. NGC 3628 served as a cautionary case: an early custom v5 imaging washed the signal down to $4.71\sigma$; returning to the ALMA pipeline standard product recovered $\text{S/N} = 15.81$ and $F = 0.982$ Jy·km/s, consistent with Toma 2024's literature value to within 2%. The pipeline product is preferred unless there is a specific reason (e.g. published baseline structure) to re-image.

Configuration surface

A new galaxy enters the pipeline with three knobs:

Knob Default When to change
z from target-list.md always set per galaxy
mode (mask connectivity) 'largest' 'all' for face-on barred spirals (multiple disjoint star-forming regions, e.g. NGC 3627)
scenario tier auto-pick from /alma-query force MS only when re-imaging is justified

Everything else — beam-convolution targets, baseline-fit degree, mask threshold, velocity-window logic — is fixed across the sample by design, so that the detection rate (7/32 ≈ 22%) is the property of the selection rather than of per-galaxy tuning.
