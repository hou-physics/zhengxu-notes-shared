About Claude Code skills

This section documents both the skills used to run the analysis and the Python code those skills orchestrate. The two are companion pieces — the skill is the workflow, the code is what the workflow runs. To make the rest of the section readable, this page explains the skill concept once.

What is Claude Code?

Claude Code is Anthropic's command-line tool for Claude — an LLM agent that reads the project's files, runs scripts, edits source, and orchestrates multi-step tasks from the terminal. It is invoked as claude in the project root.

In this thesis, Claude Code is used as the development environment for the analysis pipeline. Every galaxy in the final sample was processed through Claude Code; the methodology decisions visible in docs/rules/ were taken across many such sessions.

What is a skill?

A skill is a single Markdown file at .claude/skills/<name>/SKILL.md that defines one reusable, parameterised workflow. The file has a fixed structure:

Header (YAML frontmatter)

---
name: alma-query
description: |
  When to invoke this skill — surfaces in
  Claude's autocomplete and decision-making.
---

Body (Markdown)

  • When to use — situations the skill is for
  • Invocation patterns — examples of how it's typed
  • Step-by-step task — what the agent does, in order
  • Hard rules — things the agent must / must not do
  • Return format — what the user gets back

When you type /alma-query NGC6810 in a Claude Code session, the agent reads the matching SKILL.md, treats its body as instructions, and executes the workflow with the arguments substituted in. The skill file is the program — there is no separate compilation step or hidden binary.

Why use skills in this project?

Without skills, every per-galaxy analysis would require re-typing the same long prompt into Claude: "run /alma-query-style cone-search, filter to H30α + CO(2-1), write a step3 config, run it, check the sanity heuristics ..." Beyond the typing burden, that approach gives no reproducibility — small phrasing differences across sessions quietly produce different rankings or different masks. Encoding the workflow into a skill file solves three problems at once:

Reproducibility

The skill file is version-controlled in the project repository. Every selection or analysis run can be traced back to the exact skill revision that produced it — the methodology section's claim that "32 sources were selected by the same procedure" relies on this.

Token economy

A long, domain-loaded prompt (rule files, cube conventions, sanity heuristics) is expensive to reissue. The /analyze-galaxy skill pushes that context into a subagent that runs once per galaxy, and the main session sees only the ≤ 800-token summary. Net cost per galaxy in the main session: ~1100 tokens instead of ~9000.

Pre-flight termination

The skill can detect contradictions between the data and the rules (strong tracer missing from the cube, anomalous S/N, flux 10× a published value) and stop cleanly with a Conflict Report before producing any output. A free-form prompt would more often plough through and emit a half-result.

Chaining

Skills call other skills. /analyze-galaxy auto-invokes /update-progress on success to refresh the project's Status table without further user input. The conflict-resolution protocol can invoke /update-progress --after-rule-change. Composition keeps each skill narrow.

How a skill is used

A typical session looks like this:

# Inside the project root, start Claude Code
claude

# Then in the Claude prompt:
/alma-query NGC6810 --write-script
/analyze-galaxy NGC6810
/update-progress     # auto-invoked, usually no need to type

Each slash command triggers the agent to read the corresponding SKILL.md and execute the workflow. The user never edits the generated download_query.md, step-1_download.py, or step3_analyze.py by hand — those are skill output. Edits go into the skill file or the rule files in docs/rules/, never the per-galaxy artefacts.

The three skills used in this thesis

Skill Role
/alma-query ALMA archive cone-search, line-coverage filtering, geometric filter, sensitivity ranking; emits a Markdown selection report and an optional download script
/analyze-galaxy Resolves inputs from the project filesystem, pre-flights cube coverage, spawns a subagent that writes a per-galaxy step3_analyze.py config and runs the dual-cube pipeline
/update-progress Maintains docs/progress.md — three narrow operations (Status table, Issue Log, Next Steps cleanup) and nothing else

The pages under Code embed the Python that these skills actually run. The two are paired: a skill is the what and when, the code is the how.
