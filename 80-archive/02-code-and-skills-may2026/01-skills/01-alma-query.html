/alma-query skill

The /alma-query skill encapsulates the per-galaxy archive query documented in §2 of the Data selection methodology into a single parameterised command. Every galaxy in the final sample passed through this skill; the call signature, ranking rubric, and downstream products are kept consistent across the project so that the selection is reproducible.

What it does, one line at a time

  1. Resolve the galaxy name with NED (no manual coordinate entry).
  2. Cone-search the ALMA archive within $60''$ of the resolved position.
  3. Line filter — keep only observations whose SPWs jointly cover a weak HRL ($\text{H}n\alpha$, $n \in \{27\text{–}32,\;39\text{–}42\}$) and a same-band strong tracer (CO(2-1) / CO(1-0) / HCN(3-2) / HCO$^+$(3-2), or one of the multi-line pairs HCN(4-3), HCN(2-1), CS(2-1)).
  4. Geometric hard filter — reject sources outside $i \geq 47^\circ$, $15 \leq \text{beam}_\text{pc} \leq 150$, $D \leq 50$ Mpc, $\delta \leq +40^\circ$. Dwarf BCG sources (HyperLeda MType = Irr / I0, or undefined logR25) bypass the inclination criterion.
  5. Sensitivity threshold — drop observations with $\text{rms}_{10\,\text{km/s}} > 30$ mJy (configurable via --sens-limit-mjy).
  6. Rank by sensitivity; within a $1.5\times$ tie, prefer single-pointing over mosaic; within a remaining tie, prefer the newer project (descending observation year).
  7. Pick the cheapest product tier that is actually available — see Product tier selection below.
  8. Emit a Markdown selection report and, optionally (--write-script), a self-contained step-1_download.py script.

The skill never starts a download — the user reviews the report, then runs the script manually.

Product tier selection (Scenarios A / B / C)

The ALMA archive offers each observation in up to three forms, in ascending order of pre-processing already completed:

Scenario C — ASDM

Raw archive package as recorded at the telescope. 50–100+ GB per source. Must be calibrated via the project's scriptForPI before any imaging is possible. Used only when both A and B are unavailable; none of the 32 sources in the final sample took this path.

Scenario A — MS

Pipeline-calibrated visibility data, not yet imaged. Several hours of local CASA work per source (uvcontsub → tclean). 10–50 GB intermediate disk per source. Used when the published pipeline cube is missing, mis-cleaned, or methodologically inconsistent with the rest of the sample. Templates: step1_uvcontsub.py and step2_imaging.py.

Scenario B — FITS pbcor cube

Pipeline-imaged data cube, primary-beam-corrected, ready for direct analysis. ~MB to a few GB depending on field size. All 32 sources in the final sample were analysed via this tier, to keep the pipeline uniform and within the thesis time budget.

The auto-pick examines the URLs returned by Alma.get_data_info(mousid) and classifies each into a tier by filename pattern:

Filename pattern Tier
*.asdm.sdm C (ASDM) — checked first to beat the MS regex
*.cube.I.pbcor.fits B (FITS)
*.ms.tar or *calibrated.tar A (MS)

The cheapest available tier wins, with B preferred over A preferred over C. --force-tier FITS|MS|ASDM overrides the pick — used for methodology consistency checks (NGC 4418 was probed at MS to estimate the cost of full re-imaging; NGC 1097 likewise).

step-1_download.py is emitted with the chosen tier baked in. The Scenario B template pulls the pbcor cube and the primary-beam cube, then reconstructs the non-pbcor cube as pbcor × pb (ARI-L only publishes pbcor + PB, not the raw non-pbcor). The Scenario A template pulls the calibrated MS tar and stops there — the user runs CASA manually afterwards. Scenario C is not auto-emitted; the user runs the project's scriptForPI by hand.

Inputs and outputs

Inputs

  • galaxy — positional, single source name
  • --batch <file_or_csv> — multi-source variant
  • --weak <line> — weak HRL line name (default H30a)
  • --strong <line[,line,…]> — strong tracer names (default per band)
  • --write-script — also emit the download script
  • --force-tier {FITS,MS,ASDM} — override the auto-picked tier
  • --sens-limit-mjy <float> — pre-filter threshold
  • --pointing-max-arcsec <float> — PB-edge tolerance

Outputs

  • results/{GALAXY}/download_query.md — latest report
  • results/{GALAXY}/download_query_history/query_{ts}.md — history
  • master_thesis/my_code/{galaxy}_analyse_code/step-1_download.py — download script (only with --write-script)
  • download_urls.txt — fallback URL list, written by the download script at run time for wget -c -i resume of large downloads

CLI flags reference

Flag Purpose Default
galaxy (positional) Single galaxy name —
--batch CSV list, or path to target-list.md —
--weak Weak HRL line name H30a
--strong Comma-separated strong tracer names band-based default
--write-script Also emit step-1_download.py off
--force-tier Override the scenario pick (FITS / MS / ASDM) auto
--sens-limit-mjy Pre-filter on sensitivity_10kms (mJy) 20.0 (project uses 30)
--pointing-max-arcsec Reject candidates whose pointing centre is farther than this from the NED coordinate. Widen (e.g. 30) for sources where the nucleus lies near the primary-beam edge (NGC 7793); note that the effective rms at the source position is PB-attenuated relative to the archive-reported rms. 15.0

Common invocations

# Query a single galaxy; print the report only
/alma-query NGC6810

# Explicit weak + strong line pair
/alma-query NGC6810 --weak H30a --strong CO21,HCN32

# Also emit the download script
/alma-query NGC6810 --write-script

# Force re-imaging from MS (methodological consistency check)
/alma-query NGC6810 --write-script --force-tier MS

# Batch from the project's target list (filtered automatically)
/alma-query --batch docs/target-list.md

# Batch from an explicit comma list
/alma-query --batch "NGC6810,NGC7130,NGC3227"

What the skill does NOT do

  • Execute the download itself — --write-script emits a ready-to-run step-1_download.py (which is what the download script note documents), but the skill never invokes it. The user reviews the selection report first, then runs the emitted script manually. This separation exists so that a misclassified product tier or stale archive entry can be caught before tens of GB of download time is committed.
  • Re-image from MS automatically — for Scenario A the user runs step1_uvcontsub.py + step2_imaging.py by hand. Reasoning: tclean parameter choices (cell size, weighting, threshold) need per-galaxy judgement.
  • Calibrate ASDM — Scenario C requires manual CASA calibration via each project's scriptForPI.
  • Merge multiple projects — by design (β rule: prefer single-project solutions, so a detection cannot be attributed to inter-project flux-scale differences).
  • Silently auto-resolve unverified redshifts — NED resolution failures are flagged in the report with ⚠️ UNVERIFIED instead of being filled in from a fallback.

Why a skill rather than ad-hoc browsing

Three reasons:

  1. Reproducibility. Every selection is the deterministic output of the same code path; re-running on a different date with the same archive snapshot gives bit-identical reports. This is what allows the methodology section to claim "32 sources were selected by the same procedure" without a footnote per galaxy.
  2. Cost. A typical query takes 20–60 s end-to-end. Browsing the ALMA web interface for the same information takes 5–10 minutes per source and is impossible to audit afterwards.
  3. Selection-bias control. The hard filter encodes empirical failure modes (face-on dilution, long-baseline resolve-out, distance $1/D^2$ suppression, ALMA $\delta > +40^\circ$ horizon) that were discovered only after analysing the first $\sim 27$ galaxies. Once encoded, the same filter is applied to every subsequent candidate without exception — including retroactive checks of earlier picks.

Provenance trail

Each report carries the exact ALMA archive snapshot timestamp, the weak/strong line names, the filter settings used, and the rank order. Reports are version-controlled in the project repository, so any detection or non-detection in the final sample can be traced back to the report that selected it.
